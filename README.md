# Задание

Этот проект представляет собой тестовое задание на вакансию Python Developer, в компанию ДОМ.РФ. 
Текст задания:
```
Написать API-сервис (FastAPI, Flask) со следующими методами:
- Принять запрос. На вход передавать кадастровой номер 
(подробнее: https://ru.wikipedia.org/wiki/%D0%9A%D0%B0%D0%B4%D0%B0%D1%81%D1%82%D1%80%D0%BE%D0%B2%D1%8B%D0%B9_%D0%BD%D0%BE%D0%BC%D0%B5%D1%80) и координаты (широта, долгота)
JSON:
    {"Кадастровый номер" :"", "Координаты":{"Широта":"" , "Долгота":""}}
- Менять номер запроса в очереди запроса
- Отдать результат запроса по ID

Сервис должен отправлять запрос внешнему сервису на расчет (саму отправку реализовывать не требуется, 
но нужно понимать, что внешний сервис может выполнять расчет 10-60 секунд). 
В качестве ответа от сервиса можно взять параметры запроса с параметром calculated: true, к примеру.

Сервис должен быть запакован в Dockerfile
```
# Описание решения
## Рассмотрение бизнес требований
Поскольку, данное описание задачи звучит больше как бизнес требования к системе, то будем рассматривать их именно таковыми.
Поэтому давайте рассмотрим, что будет представлять собой сервис на уровне бизнес-логики:

### Бизнес-логика:
При прочтении данных бизнес требований, можно заметить они сформулированы очень поверхностно, 
которые можно по-разному интерпретировать, а следовательно - по-разному реализовать.

Основной сервис должен обладать функционалом:
- Создание запроса
- Изменение номера запроса в очереди
- Информация о запросе

Жизненный цикл запроса в нашем сервисе такой:

Наш сервис -> Очередь запросов -> Запрос Внешний сервис -> Результат кладется в БД

- При этом на этапе 2 мы можем изменить номер запроса в очереди.
- Получить информацию о запросе, можем в любой момент жизненного цикла.

Однако, пункт `Изменение номера запроса в очереди` c точки зрения бизнес-логики, является двойственным, 
уже на уровне написания бизнес-требований, может быть реализован по-разному.

### Трактовки:
Поэтому для внесения ясности необходимо рассмотреть несколько вариантов трактовок:
- **Трактовка первая:** номер запроса это идентификатор который мы возвращаем пользователю. 
  - ТО есть пока находиться в очереди мы можем изменить его "номер", который будет возвращаться пользователю, а не идентификатор запроса.
  - Назовем этот вариант __"Переименование Номера"__.
- **Трактовка вторая:** мы можем задавать сообщениям приоритет обработки.
  - То есть у нас есть очередь, которая имеет приоритет обработки для каждого сообщения.
  - Назовем этот вариант __"Очередь с приоритетом"__.
- **Трактовка Третья:** нам необходимо физически менять место в очереди, тем самым перетасовывая всю очередь.
  - То есть у нас есть очередь, в которой мы можем менять местами сообщения по своему усмотрению.
  - Назовем этот вариант __"Очередь с привилегиями"__.

Как видно, все эти варианты очень сильно отличаются друг от друга.

__Почему это важно:__ такие крайне расплывчатые определения на уровне бизнес требования накладывают ограничения, в зависимости от трактовки. 
В данном случае могут быть 3 различных варианта которые могут быть реализованы с применением различных технологий.
А следовательно - архитектура проекта может быть очень разной, а ее переделка - очень дорогой.
При этом ответственность за конечную реализацию лежит на разработчике/системном аналитике, а не на бизнес-аналитике, который сформулировал эти требования.

**Решение:** Давайте посмотрим на эти три варианта, уже глазами системного аналитика, и попробуем их реализовать в виде ТЗ.
И еще раз убедимся, что в бизнес анализе такие формулировки не приемлемы, так как они ведут к потенциальным проблемам.
А так же рассмотрим и реализуем возможное компромиссное решение, которое может покрыть все эти варианты трактовок.

## Системная аналитика
С точки зрения системной аналитики, все три варианта выглядят одинаково и стандартно:

У нас есть REST API, который имеет 3 метода (route)
- Route 1 - принимает запрос, создает идентификатор запроса, кладет запрос в очередь и отдает идентификатор запроса пользователю.
- Route 2 - принимает идентификатор запроса и читает данные из БД.
- Route 3 - принимает идентификатор запроса и меняет номер запроса в очереди.

Параллельно, есть процесс, который берет запросы из очереди, и обрабатывает их:
- Создает запись в БД с результатом запроса - Находится в обработке.
- Ходим в стороний сервис, который Рассчитывает результат запроса.
- Обновляем запись в БД с результатом запроса - Выполнен и результатом расчета.

С одной стороны, стек вырисовывается довольно простой:
- Сервис: FastAPI
- База данных: По описанию данных можно использовать SQLite (Позже будет выбран PG из-за одного ньанса)
- Celery в качестве параллельного процесса-обработчика.
- Очередь: ....

Однако для выбора технологии очереди, нам необходимо учесть пункт 2, который изначально внес двоякость в наши требования.
Рассмотрим это подробнее в каждом из случаев:

### Выбор технологии 

Выбор конкретной технологии очереди напрямую зависит от трактовки и каждая технология может иметь свои плюсы и минусы.

**Трактовка первая:** __"Переименование Номера"__
  - В этом случае мы в нашем обработчике никак не должны опираться на номер запроса, который мы возвращаем пользователю.
  - Нужен еще один ID, который будет уникальным и неизменяемым. те Опорным
  - При изменении номера пользователя, мы должны заменить его на Уникальный ID.
  - Эти 2 вида ID нам необходимо жестко связать.

то есть: У нас появляется 2 ID: Идентификатор запроса, который отдается пользователю, и Опорный. 
Из этого можно выделить несколько минусов такого решения:

__`Минусы`:__
- Данные ключи необходимо хранить жесткой связкой, а это так или иначе потребует DI.
- Изменение номера пользователя, крайне тяжелая операция, которая относится к уроню бизнес логики, а не к уровню данных, к которым можно отнести опорный ID.
- Желательно вести учет изменения ID пользователей, что тоже усложнит логику и сделает БД сложнее.
- Логика получения ID пользователя, немного теряет смысл.

__`Плюсы` :__
- Бизнес требования удовлетворены, бизнес аналитик молодец

__Решение для реализации этого пункта__ :
- Данное решение никак не влияют на технологии очереди. Можно использовать любую.
- При отправке запроса в необходимо создать уникальный ID, и необходимо создать пользовательский UUID.
- Для обеспечения жесткого связывания, необходимо хранить в БД эти оба индекса связанным. Например, двумя отдельными колонками одной записи БД.
- Параллельно требуется вторая таблица, которая будет хранить все изменения ID пользователей.
- Для скорости получения данных можно покрыть оба поля составным индексом. 
- Обычного Hash индекса будет не достаточно, так как он плохо совместим с работой с массивом (Операция IN) при операции создания нового пользовательского ID.  
- __Ограничение по технологии__: SQLite Такой задачи не годится и уже необходимы "полноценные" СУБД типа Postgres.
  - Такая операция для оптимального выполнения требует от БД индекса уровня GIN/GIST, который не поддерживается в SQLite. 
  - При использовании индекса уровня B-Tree, необходимо использовать ANY В запросе для оптимального поиска. Но оператор ANY не поддерживается в SQLite.

Таким образом из-за неверной трактовки бизнес требований, 
мы получаем заметную дополнительную сложность алгоритма, существенные ограниячения по технологиям связанные с выполенниям этого алгоритма и большие требования к квалификации конечного разработчика. 
А это свою очередь потребует больших затрат, в лучшем случаена этапе проективания системы, в худшем - на этапе эксплуатации.

_Вот так, криво написанное ТЗ бизнес аналитиком может привести к необоснованным сложностям и гипотетическим финансовым потерям, которые можно было бы избежать._

**Трактовка вторая:** __"Очередь с приоритетом"__.
  - В этом случае, мы во время работы с очередью, кладем ее с приоритетом обработки.
  - Нам на уровне сервиса принятия запроса необходимо задать ID запроса и приоритет обработки.
    - Этот Приоритет обработки, должен быть частью данных входа запроса и частью описательной информационной модели логики, так как именно эти данные опирается бизнес логика приложения.
  - Изменить приоритет обработки запроса, когда сообщение уже находится в классической очереди FIFO/LIFO - нельзя.
  - Поэтому нам необходимо разделить плоский сервис из 2x логических частей, которые соединяет эта очередь, на 3 части: Сервис хранилища, сервис очереди и сервис обработки. 
    - Сервис хранилища - Кладет в БД все данные, которые необходимы для хранения и генерирует ID запроса и Приоритет обработки.
    - Сервис очереди - Смотрит изменения в БД и обрабатывает их в соответствии с приоритетом.
    - Сервис обработки - Выполняет запрос и обновляет статус в БД.
  - До времени обработки записи в сервисе очереди, мы можем менять приоритет обработки.
  - Возникает вопрос: а можно ли сразу задавать приоритет обработки?
    - Соответственно, поднимается вопрос об необходимости аутентификации пользователя, для безопасности данных.

то есть: У нас появляется дополнительный логический уровень, и одно измерение в модели данных, которые напрямую влияют на бизекс-логику. 
Из этого можно выделить несколько минусов такого решения:

-  `Плюсы` - Можно это использовать классическую очередь FIFO. Для этого подойдут и стандартные инструменты FastAPI или же что то типа RabbitMQ
	-  `Минусы` - Невозможность сделать ничего кроме как изменить приоритет обработки. То есть не получиться очень важного человека пропустить без очереди.     


**Трактовка третья:** __"Очередь с привилегиями"__.

__`Минусы`:__
- Крайне сужает стек технологий, потому что выходит за рамки класcической FIFO, и заставляет писать различные ухищрения. Например - крайне важна будет дополнительная информация по величине свой очереди и не только.     
то уже не совсем очередь, а необходима поддержка классических действий с массивами. 
- Реализация уже очень сильно зависит от размеров самой очереди. И классическое нарезание массива и полная перезапись элементов может не помочь. Одно дело хранить в рантайме очередь из 100 элементов, другое дело - хранить из 1000000. Поэтому крайне важно подобрать нужную технологию сразу и правильно подобрать команды.

__`Плюсы` :__
- Бизнес требования удовлетворены, бизнес аналитик молодец
- Можно это использовать классическую очередь FIFO. Для этого подойдут и стандартные инструменты FastAPI и Брокер очередей RabbitMQ, не поднимая что то тяжелое типа Kafka/NUT.
